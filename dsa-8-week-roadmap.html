Why These Patterns, and Why This Weighting

Research into 2025-2026 interview-prep resources (NeetCode 150, Blind 75, Grind 75, LeetCode company-tag repositories, and discussion-board "most repeated questions" round-ups) converges on the same short list of high-yield categories: Arrays/Hashing, Two Pointers, Sliding Window, Binary Search, Trees/Graphs (BFS/DFS/Union-Find/Topological Sort), Heaps, Backtracking, and Dynamic Programming are named as the backbone of general software-engineering interviews across Google, Meta, Amazon, Microsoft, and most mid-size/product companies, with Dynamic Programming and Graphs consistently flagged as the hardest and most differentiating for mid-to-senior loops. Segment Trees, Fenwick Trees, heavy graph theory (Dijkstra/MST at competitive-programming depth), and advanced string algorithms (KMP, Manacher, suffix arrays) are deliberately excluded — they show up occasionally but are not general-interview staples, and including them would dilute time better spent mastering the 22 patterns below.

Patterns were not weighted equally. Arrays & Hashing, Sliding Window, Trees, and Graphs get the most problems because they appear in the largest share of real interview loops and because they compose with almost every other pattern (a graph problem is usually BFS + hashing + queue). Tries, Topological Sort, and Union-Find get few problems because they are narrower — high value when they show up, but they show up less often, and once you've internalized the template, extra repetition has low marginal return.

1. Arrays & Hashing

What it is: Using unordered_map/unordered_set to trade space for O(1) average lookup, turning an O(n²) "check every pair/every occurrence" brute force into O(n). Recognize it when: "Have I seen this before?", "count occurrences", "find a pair/group that sums/matches", "check for duplicates" → think hash map/set. Simple example → brute force → optimal: Two Sum: brute force checks every pair (O(n²)); optimal stores value → index in a map while scanning once (O(n)), checking target - nums[i] against the map before inserting. C++ template:

unordered_map<int,int> seen; // value -> index (or count)
for (int i = 0; i < n; i++) {
    if (seen.count(target - nums[i])) return {seen[target-nums[i]], i};
    seen[nums[i]] = i;
}

Common variations: counting frequencies, grouping by a computed key (sorted string, character count signature), prefix/suffix product or count tricks, detecting cycles/duplicates via a "seen" set. Common mistakes: using map (O(log n)) when unordered_map (O(1) avg) suffices; forgetting hash collisions make worst case O(n) (rarely matters at interview scale); off-by-one when the map must be built before vs during the scan; forgetting unordered_map/set don't preserve order. C++ tools: unordered_map, unordered_set, map (when sorted keys needed), vector, sort(), string building with string + to_string.

2. Two Pointers

What it is: Two indices moving through a (usually sorted) structure from the ends inward, or one behind the other, to avoid nested loops. Recognize it when: "sorted array + pair/triplet that meets a target", "compare from both ends", "in-place partition/reorder" → think Two Pointers. Simple example → brute force → optimal: 3Sum: brute force is O(n³) triple loop; optimal sorts (O(n log n)), fixes one element, then uses two pointers converging on the remaining sorted subarray for O(n) per fixed element → O(n²) total. C++ template:

sort(nums.begin(), nums.end());
int l = 0, r = n - 1;
while (l < r) {
    int sum = nums[l] + nums[r];
    if (sum == target) { /* record */ l++; r--; }
    else if (sum < target) l++;
    else r--;
}

Common variations: opposite-direction pointers on sorted arrays (pair/triplet sums), same-direction "slow/fast" pointers for in-place array editing (remove duplicates, move zeroes), two pointers on two different arrays/strings (merge, subsequence check). Common mistakes: forgetting to skip duplicate values after finding a match (classic 3Sum bug); using two pointers on an unsorted array where sorting isn't allowed (destroys original order/indices — check if the problem needs original indices); off-by-one on l < r vs l <= r. C++ tools: sort(), vector::erase/index overwriting for in-place edits, swap().

3. Sliding Window

What it is: A window [left, right] that expands and shrinks over a contiguous run of an array/string, maintaining a running condition (count, sum, set of chars) so you never re-scan the same elements. Recognize it when: "contiguous subarray/substring" + "longest/shortest/max/min that satisfies a condition" → think Sliding Window. If the window size is fixed, it's simpler (just add-one/remove-one as you slide); if variable, you grow right until invalid, then shrink left until valid again. Simple example → brute force → optimal: Longest Substring Without Repeating Characters: brute force checks every substring (O(n²)/O(n³)); optimal expands right, and whenever a repeat is found, jumps left forward past the previous occurrence, each character visited O(1) amortized times → O(n). C++ template:

int left = 0, best = 0;
unordered_map<char,int> count;
for (int right = 0; right < n; right++) {
    count[s[right]]++;
    while (/* window invalid */) {
        count[s[left]]--;
        left++;
    }
    best = max(best, right - left + 1);
}

Common variations: fixed-size window (max average/sum), variable window with a frequency map (longest substring with ≤K distinct / at most K replacements), window that must contain all of another string's characters (minimum window substring), monotonic-deque window (sliding window maximum). Common mistakes: shrinking the window with if instead of while (window becomes invalid again next iteration); forgetting to update best at the right point (before or after shrinking, depending on problem); not handling the count map correctly when a character's count hits zero (should erase or check == 0, not just < 0). C++ tools: unordered_map<char,int>, deque<int> (for sliding window maximum), two-pointer indices, min/max.

4. Prefix Sum

What it is: Precomputing cumulative sums so any range-sum query becomes O(1) subtraction instead of O(n) re-summation; often paired with a hash map to count how many prefixes hit a target. Recognize it when: "subarray sum equals K", "range sum query (many queries)", "number of subarrays with property X" → think Prefix Sum (+ HashMap if counting). Simple example → brute force → optimal: Subarray Sum Equals K: brute force checks every subarray (O(n²)); optimal keeps a running prefix sum and a map of prefixSum → count seen so far — for each index, check if prefixSum - k has been seen → O(n). C++ template:

unordered_map<int,int> prefixCount{{0,1}};
int sum = 0, result = 0;
for (int x : nums) {
    sum += x;
    if (prefixCount.count(sum - k)) result += prefixCount[sum - k];
    prefixCount[sum]++;
}

Common variations: 2D prefix sums for matrix range queries, prefix XOR instead of prefix sum, prefix sum + modulo for "divisible by K" counting. Common mistakes: forgetting to seed the map with {0: 1} (needed for subarrays starting at index 0); confusing "sum of subarray [i,j]" with prefix[j] - prefix[i] vs prefix[j] - prefix[i-1] off-by-one; recomputing prefix sums inside a loop (defeats the purpose). C++ tools: unordered_map<long long,int> (use long long — sums overflow int easily), vector<vector<int>> prefix tables for 2D.

5. Binary Search

What it is: Halving a search space each step. Two flavors: (a) classic search on a sorted array, (b) "binary search on the answer" — guessing a numeric answer and using a feasibility check to decide whether to search higher or lower. Recognize it when: "sorted array, find X in O(log n)" → classic binary search. "Minimize the maximum / maximize the minimum", "find the smallest value such that condition(value) is true" → binary search on the answer — this is a 2025-2026 trending interview pattern, don't skip it. Simple example → brute force → optimal: Koko Eating Bananas: brute force tries every possible eating speed linearly (O(max_speed × n)); optimal binary-searches the speed itself — for a guessed speed, check in O(n) if Koko finishes in time; monotonic feasibility (higher speed always finishes at least as fast) makes binary search valid → O(n log(max_speed)). C++ template (classic):

int lo = 0, hi = n - 1;
while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (nums[mid] == target) return mid;
    else if (nums[mid] < target) lo = mid + 1;
    else hi = mid - 1;
}

C++ template (on the answer):

int lo = minPossible, hi = maxPossible;
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (feasible(mid)) hi = mid;       // mid works, try smaller
    else lo = mid + 1;                  // mid too small, need bigger
}
// lo == hi is the answer

Common variations: search in rotated sorted array (figure out which half is sorted first), search for a boundary (first/last occurrence, first true in a boolean-monotonic array), binary search on 2D matrices, binary search on answer (allocation/capacity/speed minimization). Common mistakes: mid = (lo + hi) / 2 overflow on large arrays (use lo + (hi-lo)/2); infinite loops from using <= with the wrong bound update in the "on the answer" template (must shrink strictly each iteration); off-by-one between hi = mid and hi = mid - 1 — decide up front whether mid can still be the answer. C++ tools: lower_bound(), upper_bound(), binary_search(), sort() (a lot of binary search problems require a sorted precondition or come after sorting).

6. Linked Lists (+ Fast & Slow Pointers)

What it is: Pointer manipulation on singly/doubly linked nodes, plus the "fast & slow pointer" (tortoise-and-hare) trick for cycle detection and finding midpoints without extra space. Recognize it when: any linked-list restructuring (reverse, reorder, merge) → use a dummy head + careful pointer rewiring. "Detect a cycle", "find the middle", "find where a cycle starts", "find a duplicate using array-as-linked-list" → think Fast & Slow Pointers. Simple example → brute force → optimal: Linked List Cycle: brute force stores every visited node in a hash set (O(n) space); optimal uses two pointers, one stepping 1 node/iteration and one stepping 2 — if there's a cycle they must meet, using O(1) space. C++ template (reverse):

ListNode* prev = nullptr;
while (head) {
    ListNode* next = head->next;
    head->next = prev;
    prev = head;
    head = next;
}
return prev;

C++ template (fast/slow):

ListNode *slow = head, *fast = head;
while (fast && fast->next) {
    slow = slow->next;
    fast = fast->next->next;
    if (slow == fast) { /* cycle found */ }
}

Common variations: merge K sorted lists (heap or divide-and-conquer), reverse in groups of K, deep-copy a list with random pointers, detect and return the start of a cycle (needs a second pass after meeting). Common mistakes: losing the reference to next before rewiring (always save it first); forgetting a dummy head node for problems that might delete/change the actual head (avoids special-casing); null-pointer crashes from not checking fast && fast->next before dereferencing. C++ tools: raw pointers/ListNode*, a dummy sentinel node pattern, priority_queue (for merging K lists).

7. Stack & Monotonic Stack (+ Queue/Deque)

What it is: LIFO structure for tracking "most recent unresolved item" — parentheses matching, expression evaluation, and undo-style history. The monotonic stack variant keeps elements in increasing/decreasing order, popping whenever the new element breaks the order, which is exactly how you find "next greater/smaller element" in O(n) instead of O(n²). Queues/deques get their spotlight in BFS (Pattern 13) and sliding-window-maximum (Pattern 3) rather than as a standalone bucket here. Recognize it when: "matching pairs" (parentheses, tags) → stack. "Next/previous greater or smaller element", "daily temperatures until warmer", "span of previous smaller elements" → think Monotonic Stack. Simple example → brute force → optimal: Daily Temperatures: brute force scans forward from each day until a warmer day is found (O(n²)); optimal keeps a stack of indices with decreasing temperatures — when a warmer day arrives, pop and resolve every colder day at once → O(n). C++ template (monotonic stack):

stack<int> st; // stores indices, values decreasing bottom to top
vector<int> answer(n, 0);
for (int i = 0; i < n; i++) {
    while (!st.empty() && arr[st.top()] < arr[i]) {
        int idx = st.top(); st.pop();
        answer[idx] = i - idx; // or arr[i], depending on problem
    }
    st.push(i);
}

Common variations: valid parentheses / balanced brackets, min-stack (track running min alongside values), evaluate postfix/infix expressions, largest rectangle in histogram (monotonic stack + area calc), asteroid collision (simulate with a stack). Common mistakes: pushing values instead of indices onto a monotonic stack (you often need the distance/index, not just the value); forgetting to pop everything left in the stack at the end (unresolved elements usually map to a default answer like -1 or 0); using stack when you actually need random access (should be vector acting as a stack, or a deque). C++ tools: stack<int>, vector as an explicit stack (for indexed access), deque<int>.

8. Heap / Priority Queue

What it is: A binary heap that gives O(1) access to the min or max element and O(log n) insert/remove — the go-to structure whenever you repeatedly need "the current smallest/largest of a changing set." Recognize it when: "Kth largest/smallest", "Top K", "K closest points", "merge K sorted things", "median of a stream" → think Heap. Simple example → brute force → optimal: Kth Largest Element in an Array: brute force sorts the whole array every time (O(n log n)); optimal keeps a min-heap of size K — anything smaller than the heap's top gets discarded, so the heap always holds the K largest, and the answer is the top → O(n log K). C++ template (min-heap of size K, for "K largest"):

priority_queue<int, vector<int>, greater<int>> minHeap;
for (int x : nums) {
    minHeap.push(x);
    if (minHeap.size() > k) minHeap.pop();
}
// minHeap.top() is the Kth largest

Common variations: two heaps for a running median (max-heap for lower half, min-heap for upper half), heap of pairs/custom comparator for K closest points or task scheduling, heap-based Dijkstra-lite problems (IPO, network delay). Common mistakes: forgetting C++'s priority_queue is a max-heap by default — you must pass greater<int> explicitly for a min-heap; writing a comparator backwards (comparator returns true when the first argument should come after the second, which feels inverted the first few times); pushing raw values when you need to push {value, index} pairs to recover positions later. C++ tools: priority_queue<T, vector<T>, Comparator>, custom comparator structs or lambdas, pair<int,int> for value+index heaps.

9. Intervals

What it is: Problems about ranges [start, end] that must be sorted (almost always by start time) and then swept left-to-right, merging or comparing overlaps as you go. Recognize it when: "overlapping intervals", "meeting rooms", "free time", "minimum arrows/removals to eliminate overlap" → think Sort by start, then sweep. Simple example → brute force → optimal: Merge Intervals: brute force compares every pair of intervals for overlap (O(n²)); optimal sorts by start (O(n log n)), then does a single pass merging the current interval into the last one whenever they overlap → O(n log n) total. C++ template:

sort(intervals.begin(), intervals.end());
vector<vector<int>> merged;
for (auto& iv : intervals) {
    if (!merged.empty() && iv[0] <= merged.back()[1])
        merged.back()[1] = max(merged.back()[1], iv[1]);
    else
        merged.push_back(iv);
}

Common variations: insert a new interval into an already-sorted list, count minimum meeting rooms needed (heap of end times, or separate start/end event sweep), minimum arrows to burst overlapping balloons (sort by end, not start), find gaps/free time between busy intervals. 10. Trees (Binary Tree Core)

What it is: Recursive traversal and property computation on binary trees — nearly every tree problem is "do something at this node, then recurse on left and right, then combine." Recognize it when: any problem on a TreeNode structure without ordering guarantees (that's Pattern 11) → think recursive DFS first, level-by-level output → think BFS with a queue. Simple example → brute force → optimal: Maximum Depth of Binary Tree: there isn't really a "brute force" here — the insight is that depth(node) = 1 + max(depth(left), depth(right)), with depth(null) = 0. The "optimal" pattern is the recursive definition; the teaching point is recognizing that many tree problems are answered by writing this kind of recurrence directly. C++ template (recursive DFS):

int solve(TreeNode* node) {
    if (!node) return /* base case */;
    int left = solve(node->left);
    int right = solve(node->right);
    return /* combine left, right, node->val */;
}

C++ template (BFS level order):

queue<TreeNode*> q; q.push(root);
while (!q.empty()) {
    int sz = q.size();
    for (int i = 0; i < sz; i++) {
        TreeNode* node = q.front(); q.pop();
        // process node (this level)
        if (node->left) q.push(node->left);
        if (node->right) q.push(node->right);
    }
}

Common variations: level-order traversal (BFS), path-sum problems (carry a running value down the recursion), "diameter"-style problems where the answer isn't at the root (use a global/reference variable updated inside the recursion), tree construction from traversal arrays, tree serialization. Common mistakes: forgetting the null-node base case (instant crash or wrong answer); computing an answer that requires "the best path through this node" but only returning "the best path starting at this node" upward — these are different values and mixing them up is the #1 tree-DP bug; using global mutable state carelessly across multiple test calls (reset it). C++ tools: TreeNode* recursion, queue<TreeNode*> for BFS, stack<TreeNode*> for iterative DFS.

11. Binary Search Trees

What it is: Binary trees with the ordering invariant left < node < right, which lets you binary-search, and makes an in-order traversal produce sorted output for free. Recognize it when: the problem explicitly says BST, or mentions "sorted", "Kth smallest", "closest value" on a tree → use the ordering to prune one side, or use in-order traversal to get sorted order for free. Simple example → brute force → optimal: Kth Smallest Element in a BST: brute force does a full in-order traversal into an array, then indexes it (O(n) space); optimal does an in-order traversal and stops as soon as it has visited K nodes, using O(h) space (no array). C++ template (validate using bounds):

bool valid(TreeNode* node, long lo, long hi) {
    if (!node) return true;
    if (node->val <= lo || node->val >= hi) return false;
    return valid(node->left, lo, node->val) && valid(node->right, node->val, hi);
}

Common variations: validate BST (careful with bounds, not just comparing to immediate children), lowest common ancestor using ordering (no need to search both sides), delete/insert while maintaining the invariant, convert sorted array to a balanced BST (pick the middle as root, recurse). Common mistakes: validating a BST by only comparing a node to its direct children (misses violations from grandparents — must pass down a valid range); using int bounds for the range check when values can hit INT_MIN/INT_MAX (use long); doing an unnecessary full traversal when the BST property lets you go directly left or right. C++ tools: recursive bound-passing, stack<TreeNode*> for iterative in-order (BST iterator problems), long/long long for bound sentinels.

12. Tries (Prefix Trees)

What it is: A tree where each path from the root spells out a prefix of some stored string, so prefix search, autocomplete, and "does this word/prefix exist" become O(word length) instead of O(number of words). Recognize it when: "prefix", "autocomplete", "dictionary of words", "word search with many query words" → think Trie. Simple example → brute force → optimal: Implement Trie: brute force stores words in a hash set and checks startsWith by scanning every word (O(n·L)); optimal builds a 26-way (or map-based) tree where each node holds children and an "is end of word" flag, making insert/search/startsWith all O(L), independent of how many words are stored. C++ template:

struct TrieNode {
    TrieNode* children[26] = {};
    bool isEnd = false;
};
void insert(TrieNode* root, const string& word) {
    TrieNode* node = root;
    for (char c : word) {
        int i = c - 'a';
        if (!node->children[i]) node->children[i] = new TrieNode();
        node = node->children[i];
    }
    node->isEnd = true;
}

Common variations: search with wildcard characters (needs DFS/backtracking through the trie instead of a straight walk), building a trie over a grid of letters to speed up multi-word search (Word Search II), storing additional metadata at each node (word count, full word at terminal nodes). Common mistakes: using a unordered_map<char, TrieNode*> when a fixed array<TrieNode*, 26> would be faster and simpler for lowercase-only inputs; forgetting the isEnd flag (without it you can't distinguish "abc" from "ab" being a prefix vs. a stored word); memory leaks from new without cleanup (usually fine to ignore at interview scale, but mention it if asked). C++ tools: custom struct TrieNode, array<TrieNode*, 26> or unordered_map<char, TrieNode*>, recursion/backtracking for wildcard search.

13. Graphs — BFS & DFS

What it is: Traversing nodes/edges (often an implicit grid, sometimes an adjacency list) while tracking visited state, to find connectivity, shortest paths (unweighted), or explore all reachable states. Recognize it when: "shortest path in an unweighted graph/grid" → think BFS. "Explore all connected pieces / does a path exist / count islands/regions" → DFS or BFS, either works — DFS is usually shorter to write, BFS is required if you need shortest distance. Simple example → brute force → optimal: Number of Islands: brute force isn't really applicable — you must visit each cell; the "optimal" insight is marking cells visited in place (flip '1' to '0', or use a visited set) so you never re-count the same island, giving O(rows × cols). C++ template (BFS on a grid):

queue<pair<int,int>> q; q.push({sr, sc}); visited[sr][sc] = true;
int dirs[4][2] = {{0,1},{0,-1},{1,0},{-1,0}};
while (!q.empty()) {
    auto [r, c] = q.front(); q.pop();
    for (auto& d : dirs) {
        int nr = r + d[0], nc = c + d[1];
        if (nr>=0 && nr<rows && nc>=0 && nc<cols && !visited[nr][nc] && grid[nr][nc] != obstacle) {
            visited[nr][nc] = true;
            q.push({nr, nc});
        }
    }
}

Common variations: multi-source BFS (push all sources into the queue before starting — e.g. Rotting Oranges), DFS with backtracking to find all paths, graph cloning (DFS/BFS + a hash map from old node → new node), word-transformation graphs where each valid one-letter change is an edge (Word Ladder). Common mistakes: forgetting to mark a node visited at the moment you enqueue it (not when you dequeue it) — marking on dequeue causes duplicate enqueues and wrong BFS distances; not checking grid bounds before indexing; using DFS recursion on a huge grid and blowing the call stack (BFS or an explicit stack avoids this). C++ tools: queue, unordered_map<Node*, Node*> for cloning, vector<vector<bool>> visited grids, unordered_set for visited nodes in general graphs.

14. Topological Sort

What it is: Ordering nodes in a directed graph so every edge u → v places u before v — only possible if there's no cycle. Built with either repeated removal of zero-in-degree nodes (Kahn's/BFS) or DFS with post-order. Recognize it when: "prerequisites", "dependencies", "build order", "course schedule" → think Topological Sort, and remember it doubles as cycle detection (if you can't produce a full ordering, there's a cycle). Simple example → brute force → optimal: Course Schedule: brute force would try every ordering (factorial); optimal computes in-degree for every course, repeatedly pops zero-in-degree courses into the order and decrements their neighbors' in-degree — if every course gets placed, there's no cycle; if some are left over, a cycle exists → O(V + E). C++ template (Kahn's algorithm):

vector<int> indegree(n, 0);
for (auto& e : edges) indegree[e[1]]++;
queue<int> q;
for (int i = 0; i < n; i++) if (indegree[i] == 0) q.push(i);
vector<int> order;
while (!q.empty()) {
    int u = q.front(); q.pop();
    order.push_back(u);
    for (int v : adj[u]) if (--indegree[v] == 0) q.push(v);
}
// order.size() < n  =>  cycle exists

Common variations: returning the actual valid order vs. just a yes/no on feasibility, lexicographically smallest valid order (use a priority_queue instead of a plain queue in Kahn's), detecting cycles in a directed graph with DFS + a "currently in recursion stack" marker. Common mistakes: applying topological sort logic to an undirected graph (it doesn't apply — undirected cycle detection uses Union-Find or plain DFS with a parent check instead); forgetting that a course/node with zero dependencies from the start still needs to be output; not detecting cycles at all (silently returning a partial/wrong order). C++ tools: queue<int>, vector<vector<int>> adj adjacency list, vector<int> indegree, priority_queue for lexicographic variants.

15. Union-Find (Disjoint Set Union)

What it is: A structure that tracks which "group" each element belongs to and can merge two groups (union) or check if two elements are in the same group (find) in near-O(1) amortized time using path compression + union by rank. Recognize it when: "connected components", "redundant connection / cycle in an undirected graph", "group accounts/islands that share something", "will adding this edge create a cycle" → think Union-Find. Simple example → brute force → optimal: Redundant Connection: brute force re-checks connectivity with a fresh BFS/DFS for every edge (O(n²)); optimal processes edges one at a time, union-ing their endpoints — the first edge whose endpoints are already in the same set is the redundant one → nearly O(n α(n)) ≈ O(n). C++ template:

vector<int> parent, rank_;
int find(int x) { return parent[x] == x ? x : parent[x] = find(parent[x]); } // path compression
bool unite(int a, int b) {
    a = find(a); b = find(b);
    if (a == b) return false; // already connected -> would form a cycle
    if (rank_[a] < rank_[b]) swap(a, b);
    parent[b] = a;
    if (rank_[a] == rank_[b]) rank_[a]++;
    return true;
}

Common variations: counting the number of connected components, detecting a cycle while building a graph edge-by-edge, "accounts merge" style problems where the union key is derived data (shared emails) rather than plain indices, weighted union-find for "evaluate division"-style ratio problems. Common mistakes: forgetting path compression (parent[x] = find(parent[x])), which turns find from O(n) worst case back into near O(1); implementing unite without union by rank/size (still correct, just slower on adversarial inputs); off-by-one when mapping non-integer entities (strings, emails) to array indices — build the index map carefully first. C++ tools: vector<int> parent, rank_, path-compressed recursive find, unordered_map<string,int> for mapping non-integer keys to DSU indices.

16. Greedy

What it is: Making the locally-best choice at each step and trusting (having proven, not just hoped) that it leads to a globally optimal answer. The hard part isn't coding it — it's recognizing when a greedy choice is actually safe, versus when it's a trap that needs DP. Recognize it when: "maximize/minimize with a simple exchange argument" (sort by one criterion, then take greedily), "can you reach the end", "assign/schedule to satisfy the most people" → think Greedy, but sanity-check with a small counter-example before committing — if you can't argue why the greedy choice is always safe, it's probably DP instead. Simple example → brute force → optimal: Jump Game: brute force tries every combination of jump lengths recursively (exponential); optimal greedily tracks the farthest index reachable so far while scanning left to right — if the farthest reachable point ever falls behind the current index, it's impossible → O(n). C++ template (reachability greedy):

int farthest = 0;
for (int i = 0; i < n; i++) {
    if (i > farthest) return false; // can't even reach index i
    farthest = max(farthest, i + nums[i]);
}
return true;

Common variations: interval scheduling (sort by end time, greedily pick non-conflicting), gas station / circular feasibility (track a running deficit, restart start point at the failure), two-pass greedy (Candy — one pass left-to-right, one right-to-left, take the max), assignment/matching greedy (cookies to children, sorted). Common mistakes: applying a greedy strategy without proving it's correct (many "obviously greedy" problems are actually DP — e.g. don't assume Coin Change is greedy, it isn't for arbitrary denominations); picking the wrong sort key (by start vs. by end changes correctness completely for interval problems); not handling the "impossible" case explicitly. C++ tools: sort() with custom comparators, running max/min trackers, no fancy data structure usually needed — the skill is the argument, not the code.

17. Backtracking

What it is: Exploring a decision tree by making a choice, recursing, and undoing the choice before trying the next one ("choose → explore → un-choose"). This is how you generate every valid combination/permutation/arrangement without writing nested loops for each position. Recognize it when: "generate all combinations/permutations/subsets", "find all valid arrangements satisfying constraints" (N-Queens, Sudoku), "partition a string/array in every valid way" → think Backtracking. Simple example → brute force → optimal: Subsets: there's no faster-than-exponential solution (2ⁿ subsets must all be produced), so the "optimization" is in how cleanly you generate them — backtracking builds each subset incrementally and prunes early when a constraint is already violated, rather than generating all 2ⁿ combinations and filtering afterward. C++ template:

void backtrack(int start, vector<int>& path, vector<int>& nums, vector<vector<int>>& result) {
    result.push_back(path); // for "all subsets" style problems
    for (int i = start; i < nums.size(); i++) {
        path.push_back(nums[i]);          // choose
        backtrack(i + 1, path, nums, result); // explore
        path.pop_back();                  // un-choose
    }
}

Common variations: permutations (use a "used" boolean array instead of a start index, since order matters), combination sum (allow reusing the same element by not advancing start), constraint-satisfaction grids (N-Queens, Sudoku — track attacked rows/columns/diagonals), string partitioning (Palindrome Partitioning — only recurse into a substring if it's currently a palindrome). Common mistakes: forgetting to un-choose (pop_back() / reset a used flag) after recursing, corrupting the path for later branches; not skipping duplicate values at the same recursion depth in "avoid duplicate subsets/combinations" variants (sort first, then skip nums[i] == nums[i-1] when i > start); pushing a copy of path at the right time (pushing a reference/pointer that later mutates gives wrong stored results — result.push_back(path) copies a vector, which is correct, but be careful with more complex state). C++ tools: recursion with a mutable path vector passed by reference, vector<bool> used, sorting before backtracking to enable duplicate-skipping.

18. Bit Manipulation

20. 1-D Dynamic Programming

What it is: Breaking a problem into overlapping subproblems indexed by a single variable (usually "up to index i"), where dp[i] depends on a small number of earlier dp[j] values, and caching results so each subproblem is solved once. Recognize it when: "count the number of ways to...", "maximum/minimum value achievable up to position i", and — the strongest signal — when your first working solution is a brute-force recursion that recomputes the same state many times. → think 1-D DP. Mental checklist: (1) can I write the brute-force recursion? (2) does it call itself with the same arguments repeatedly? (3) if yes, memoize it, then optionally convert to a bottom-up array. Simple example → brute force → optimal: House Robber: brute-force recursion tries "rob this house" or "skip it" at every index (O(2ⁿ)); noticing solve(i) only depends on solve(i-1) and solve(i-2) leads to dp[i] = max(dp[i-1], dp[i-2] + nums[i]), computed bottom-up in O(n) time, O(1) space if you only keep the last two values. C++ template (bottom-up):

vector<int> dp(n + 1);
dp[0] = base0; dp[1] = base1;
for (int i = 2; i <= n; i++)
    dp[i] = /* combine dp[i-1], dp[i-2], ... */;
return dp[n];

C++ template (top-down memoization — write this first if the recurrence isn't obvious):

unordered_map<int,int> memo;
int solve(int i) {
    if (/* base case */) return baseValue;
    if (memo.count(i)) return memo[i];
    return memo[i] = /* recurrence using solve(i-1), solve(i-2)... */;
}

Common variations: counting ways (Decode Ways, Climbing Stairs), max/min value along a sequence (House Robber, Maximum Subarray/Kadane's), string segmentation (Word Break — dp[i] = can the prefix of length i be segmented), circular-array variants (House Robber II — run the linear version twice, excluding first or last element). Common mistakes: writing the recursion but forgetting to memoize (still exponential); getting base cases wrong (off-by-one between dp[0] meaning "empty" vs. "first element"); trying to jump straight to the bottom-up array without first confirming the recurrence via brute-force recursion — this is the #1 reason people freeze on new DP problems in interviews. Always derive the recurrence from a brute force first. C++ tools: vector<int> / vector<long long> for dp arrays, unordered_map<int,int> for memoization when indices are sparse or multi-dimensional-but-small, careful long long casting to avoid overflow in "count the ways" problems.

21. 2-D DP / Knapsack-Style

What it is: DP where the state needs two dimensions — typically "position in a grid" (row, col) or "index into items, remaining capacity" (the classic knapsack shape: for each item, decide include vs. exclude, subject to a budget). Recognize it when: "grid, moving only right/down, count paths or minimize cost" → grid DP, dp[r][c] depends on dp[r-1][c] and dp[r][c-1]. "Subset of items, each used at most once (or unlimited times), hit exactly/at most a target capacity/sum" → think 0/1 Knapsack (each item once) or Unbounded Knapsack (items reusable, like Coin Change II). Simple example → brute force → optimal: Unique Paths: brute force recursively tries every right/down move (O(2^(m+n))); optimal builds dp[r][c] = dp[r-1][c] + dp[r][c-1] (number of ways to reach each cell = sum of ways to reach the cell above and the cell to the left) in O(rows × cols). C++ template (grid DP):

vector<vector<int>> dp(rows, vector<int>(cols));
for (int r = 0; r < rows; r++)
    for (int c = 0; c < cols; c++) {
        if (r == 0 && c == 0) { dp[r][c] = base; continue; }
        dp[r][c] = /* combine dp[r-1][c], dp[r][c-1] */;
    }

C++ template (0/1 Knapsack, space-optimized to 1-D):

vector<bool> dp(target + 1, false); dp[0] = true;
for (int item : items)
    for (int cap = target; cap >= item; cap--) // iterate DOWN to avoid reusing an item
        dp[cap] = dp[cap] || dp[cap - item];

Common variations: grid DP with obstacles (skip cells that are blocked), path-sum minimization on a grid, subset-sum / partition-equal-subset (0/1 knapsack in disguise — "can we split into two equal-sum groups?"), Coin Change II (unbounded knapsack — count combinations, note the loop order is item-outer to avoid counting permutations as distinct), 2-D grid DP where a cell also depends on the min/max of a third thing (Dungeon Game requires computing backward from the goal). Common mistakes: iterating the capacity loop upward in 0/1 knapsack (reuses the same item multiple times — that's the unbounded knapsack bug when you didn't mean to); mixing up "count combinations" vs. "count permutations" via loop-nesting order (item-outer = combinations, capacity-outer = permutations — this single ordering choice is a very common interview trip-up); forgetting the base row/column (r==0 or c==0) needs its own initialization pass in grid DP, not the general recurrence. C++ tools: vector<vector<int>> 2-D dp tables, 1-D space-optimized rolling arrays, careful loop-direction reasoning (this pattern is where loop order actually changes correctness, not just style).

22. Subsequence / String DP (LCS & LIS Families)

What it is: DP over two strings/sequences being compared (Longest Common Subsequence family), or over one sequence looking for the longest ordered subsequence (LIS family), or over substrings checked for palindrome structure. These are the string-flavored DP problems that trip people up because the "obvious" 2-D table isn't always about a physical grid. Recognize it when: "longest common subsequence/substring between two strings", "edit distance / minimum operations to transform one string into another", "longest increasing subsequence", "is this a palindrome, and how do we build on smaller palindromes" → think LCS/LIS/Palindrome DP. Simple example → brute force → optimal: Longest Common Subsequence: brute force tries every subsequence of both strings (exponential); optimal builds dp[i][j] = LCS length of text1[0..i) and text2[0..j) — if the last characters match, dp[i][j] = 1 + dp[i-1][j-1]; otherwise dp[i][j] = max(dp[i-1][j], dp[i][j-1]) → O(m·n). C++ template (LCS-style 2-string DP):

vector<vector<int>> dp(m + 1, vector<int>(n + 1, 0));
for (int i = 1; i <= m; i++)
    for (int j = 1; j <= n; j++)
        dp[i][j] = (a[i-1] == b[j-1]) ? 1 + dp[i-1][j-1]
                                       : max(dp[i-1][j], dp[i][j-1]);

C++ template (LIS, O(n log n) with binary search):

vector<int> tails; // tails[k] = smallest possible tail of an increasing subsequence of length k+1
for (int x : nums) {
    auto it = lower_bound(tails.begin(), tails.end(), x);
    if (it == tails.end()) tails.push_back(x);
    else *it = x;
}
return tails.size();

Common variations: Edit Distance (three operations instead of two states — insert/delete/replace), Distinct Subsequences (counting instead of length-finding — sums instead of max), Longest Palindromic Substring / Palindromic Substrings (dp[i][j] = "is substring i..j a palindrome", built from smaller palindromes outward), Delete Operation for Two Strings (LCS in disguise — answer is m + n - 2·LCS). Common mistakes: off-by-one between 0-indexed strings and 1-indexed dp tables (the template above uses a[i-1] precisely because dp is sized m+1 to hold an empty-string base case — mixing this up is extremely common); defaulting to O(n²) LIS when O(n log n) is expected for large inputs (know both); confusing "longest common subsequence" (not contiguous) with "longest common substring" (must be contiguous, different recurrence). C++ tools: vector<vector<int>> 2-D tables with a "+1" offset for empty-prefix base cases, lower_bound() for the O(n log n) LIS trick, careful indexing discipline.

Part 7 — Mistake & Revision Strategy

You will not re-solve all 197 problems from scratch multiple times — that's a low-value use of 8 weeks. Instead, use a tiered system where only the problems that actually gave you trouble get repeated attention, and everything else gets lighter-touch review.

The Revision System

Same Day (right after solving): Before moving to the next problem, spend 2 minutes writing (mentally or in a notes doc) one sentence: "This is [pattern] because [clue in the problem]. The template is [one-line recurrence/approach]." This is the single highest-leverage habit in this entire plan — it's what converts "I solved a problem" into "I can recognize this pattern again."

Next Day: Before starting the new day's problems, spend 5-10 minutes re-attempting (from memory, no looking at your old code) whichever problem from yesterday felt hardest. If you can't reproduce it, that's fine — read your notes, not the solution, and try again.

End of Week (the Weekly Test, Part 4): A mixed, unlabeled set from that week's material. This tests pattern recognition under ambiguity, which is the actual interview skill — in a real interview nobody tells you "this is a sliding window problem."

Every 2 Weeks (Days 14, 28, 42, 56): A larger, timed, cumulative mixed session pulling from the last two weeks. This is where you catch pattern confusion that only shows up when multiple patterns are mixed together (e.g., confusing when a "contiguous subarray" problem needs Sliding Window vs. Prefix Sum — a very common real confusion, since both mention "subarray").

Three-Tier Mistake Classification

After every problem, sort it into exactly one bucket:

Tier When it applies What to do
Re-solve You got the pattern wrong, not just a bug — e.g., you tried brute force on a Sliding Window problem and never saw the window insight Re-attempt fully from scratch within 48 hours, without looking at your first attempt
Review conceptually You got the pattern right but fumbled implementation (off-by-one, wrong STL container, edge case) Re-read your one-line note and the relevant template in Part 2; you don't need to re-type the whole solution, just confirm you now see the bug
Add to mistake list Anything that took more than one attempt, regardless of tier above Goes into a running log (format below) that you sweep through entirely on Day 56

Mistake Log Template

Keep one running document (a spreadsheet or plain text file works fine) with a row per problem that gave you trouble:

Problem Pattern What went wrong The fix (one line) Tier
(example) 3Sum (#15) Two Pointers Didn't skip duplicate values after a match, got duplicate triplets After finding a match, while (l<r && nums[l]==nums[l-1]) l++; Review conceptually

By Day 56 this log becomes your single most valuable revision artifact — it's a custom "greatest hits of my own blind spots" list, far more efficient to review than re-scanning all 197 problems.

What NOT to Do

  • Don't re-solve a problem you got right on the first try just because it's been two weeks — recognition-check it in the weekly/biweekly tests instead.
  • Don't move on from a Re-solve tier problem without actually re-attempting it — reading the solution and nodding along feels like progress but doesn't build recall.
  • Don't skip writing the same-day one-liner because you're in a hurry — it takes 2 minutes and is the difference between this being a "pattern recognition" plan versus just another "200 problems solved" checkbox exercise.

Part 8 — Final Interview Preparation Strategy

How to Run Day 56 (the capstone)

  1. Morning (45 min): Take Test 8 from Part 4 as a single timed block — 8 problems, ~5-6 min each to identify the pattern and outline an approach (not fully code all 8; this is a recognition drill, not a coding marathon). Write down your pattern guess for each before checking the answer key.
  2. Afternoon: Fully code 2-3 of those 8 problems under real interview conditions (45 min each, no hints, explain your approach out loud as if to an interviewer, including time/space complexity, before writing code).
  3. Evening: Read your entire mistake log from Part 7, start to finish. For every "Re-solve" tier entry you haven't cleared yet, do one final attempt.

How Weeks 7-8 Should Feel Different From Weeks 1-6

In Weeks 1-6 the goal was learning — it's fine to look at recognition clues before attempting a problem. From Week 7 onward, treat every new problem as a mini mock interview: - Read the problem once, then talk through your approach out loud (or in writing) before coding anything, including a brute force and why it's insufficient. - State time and space complexity before you finish coding, not as an afterthought. - Write test cases yourself (including an edge case: empty input, single element, all-duplicate values) rather than only checking against the examples given. - Timebox strictly. If you're stuck past the time limit, look at only the pattern name, not the solution, and try to finish it yourself from there.

Mock Interview Practice (Beyond Day 56)

Two to three times during Weeks 7-8, run a fuller mock: pick 1-2 problems you haven't seen from this plan's "OPTIONAL" tier (they're real problems you skipped, which makes them genuinely unseen), give yourself 35-45 minutes total, and — if possible — have a friend, peer, or even a rubber duck simulate an interviewer by asking you to explain your reasoning at each step. The skill being tested in a real loop is not "can you solve this" in isolation, it's "can you solve this while narrating your thought process, handling a hint gracefully, and writing clean code under mild social pressure." Practicing silently only builds half of that skill.

Weak-Topic Revision Priority (if time is short in Week 8)

If you have to cut something in the final week, cut in this order (least costly first): OPTIONAL-tagged problems you haven't done yet → SHOULD DO problems in patterns you've already tested well on → SHOULD DO problems in patterns from your mistake log. Never cut: anything tagged MUST DO, and never cut same-day/next-day revision on problems you got wrong — those are the highest-value minutes in the entire plan.

Beyond Pure DSA (a brief note)

This plan covers algorithmic pattern recognition, which is necessary but not sufficient for a full interview loop. Two things worth 30-60 minutes total, not part of the daily problem count above: (1) a template for narrating your approach out loud in the first 60 seconds of any coding interview (restate the problem, state a brute force, state its complexity, then say what you'd optimize and why); (2) if your target roles include senior/broader loops, a short read-through of system-design and behavioral-interview basics — outside this plan's scope, but worth not leaving to the last week.
